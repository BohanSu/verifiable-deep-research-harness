# 评测运行记录与复现

本文说明批量评测产生什么文件、每个字段表示什么，以及公开 GitHub 仓库与课题提交附件应分别包含哪些内容。

## 1. 输出目录

执行：

```bash
PYTHONPATH=src python3 -m deep_research.cli eval \
  --dataset examples/tasks.jsonl \
  --output runs/evaluation.json \
  --offline
```

会得到以下结构：

```text
runs/
├── evaluation.json
└── eval-<task-id>/
    ├── final.json
    ├── events.jsonl
    ├── checkpoints.sqlite
    ├── artifacts/
    └── sources/
```

`evaluation.json` 用于跨题汇总。每一道题的原始过程仍以独立运行目录保存，因此汇总指标可以回到具体查询、工具调用、证据原文和智能体交接记录。

## 2. 六类交付信息的位置

| 交付要求 | 汇总字段 | 原始审计材料 |
| --- | --- | --- |
| 输入任务 | `input_task`、`task_id`、`dataset_sha256` | `final.json` 中的 `question` 与附件清单 |
| 工具调用轨迹 | `event_count`、`tool_event_count`、`artifacts.event_trace` | `events.jsonl` 中按时间排列的检索、抓取、智能体执行、重试和恢复事件 |
| 引用证据 | `evidence_count`、`cited_evidence_ids` | `final.json.evidence`、`artifacts/` 证据产物和 `sources/` 原文快照 |
| 最终答案 | `final_answer`、`answer_delivery` | `final.json.draft_answer` 与 `answer_delivery` |
| 评分结果 | `task_completed`、`exact_match`、`closure_score`、`citation_passed` | `final.json.closure`、`verification` 及逐目标审计项 |
| 成本与时延 | Token、调用次数、`estimated_cost_usd`、`duration_seconds` | `final.json.counters`、SQLite 用量账本及事件时间戳 |

`artifacts` 字段同时给出最终状态、事件轨迹、检查点数据库、阶段产物和来源快照的位置。`artifact_status=complete` 表示三个核心文件 `final.json`、`events.jsonl` 和 `checkpoints.sqlite` 都存在；它不等于答案一定正确，答案质量仍由相应评分字段表达。

## 3. 指标边界

- `exact_match` 保留现有开发集兼容语义：忽略大小写后，最终答案需要包含任务中配置的全部答案片段。它是本地答案键检查，不冒充 BrowseComp 或 GAIA 的官方 judge。
- 没有配置 `answers` 时，`exact_match=null` 且 `exact_match_status=not_configured`，不会把缺少 judge 错写成零分。
- `closure_score` 是系统内部证据充分度诊断分，不是事实正确概率。引用逐句检查由 `citation_passed` 单独记录。
- `estimated_cost_usd` 按模型实际返回的 Token 用量和配置价格表估算；`cost_status` 明确表示该值是否可用。用量字段的 `usage_scope=cumulative_run` 表示它们是该运行目录累计保存的总量。
- `duration_seconds` 是评测器包围单题完整 `engine.run` 调用测得的墙钟时间。新运行的 `latency_scope=fresh_end_to_end`；若同名目录已存在，则 `run_reused=true` 且 `latency_scope=resume_or_replay_invocation`，此时该时延只表示本次恢复或回放调用，不能冒充原始首次运行时延。
- 自动补证会在持久化总上限内继续检索，同时默认预留 1 轮、2 次检索和 3 页给一次明确授权的恢复。预留额度不会扩大总预算；若操作员把初始预算直接配置到总上限，运行记录会如实显示没有剩余恢复额度。
- 参考答案不复制进 `input_task`，只记录 `reference_answer_count`，降低公开结果意外泄露隐藏答案的风险。

## 4. 失败隔离

单题出现模型、搜索或解析异常时，评测器会为该题写入 `status=failed` 和截断后的 `error`，继续执行后续题目。`failure_types` 汇总研究状态中已经归因的失败类型，原始错误顺序保留在 `events.jsonl` 和 `final.json.failures`。

任务 ID 必须唯一。包含空格或路径字符的 ID 会转换为安全运行目录名，并附加原始 ID 的短哈希，避免不同题目写入同一目录。

## 5. GitHub 与课题附件

公开 GitHub 仓库应提交源码、测试、`.env.example`、价格表、可公开的数据集定义和本说明。`.env`、`.cache/` 与 `runs/` 已被 `.gitignore` 排除，因为其中可能包含 API 配置关联信息、受版权约束的网页快照和大量运行数据。

课题验收时应单独提交冻结后的实验附件，至少包含：

1. 使用的数据集文件或数据集版本与哈希。
2. `evaluation.json` 汇总。
3. 汇总中每个 `run_id` 对应的完整运行目录。
4. 模型 ID、搜索提供方、预算、价格表和代码提交哈希。
5. 官方 judge 或人工评分输出，以及执行命令和环境版本。

当前仓库只提供 `examples/tasks.jsonl` 离线冒烟任务。官方 BrowseComp、GAIA 题目文件和隐藏答案 judge 尚未提供，因此现有结果只能证明评测链路可运行，不能作为官方基准成绩。
